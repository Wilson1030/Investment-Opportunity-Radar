# 06 · 策略设计总表

> **设计全量，实现逐个**（D13）。本文件为 **10 类 Thesis 提供完整设计**：规则条件、评分规则、
> 失效条件、待确认模板、阶梯、风险权重、以及每类策略特有的**反例警示**。
>
> 原始规格 §5.6 用 10 个示例说明「系统不应只围绕 ST / 重组」。这 10 个示例在本文件中被正式化为
> 10 个 `ThesisTypeDef`，全部写入 `strategies/registry.py`；本条实现状态见下表。

---

## 1. `ThesisTypeDef` 统一字段

```yaml
code:                      # ThesisType 枚举值
display_name:              # 中文名
status:                    # implemented | designed | planned
user_goal:                 # 用户目标（来自 §5.6 示例）
description:               # 一句话逻辑
core_conditions:           # 核心条件清单 → 用于计算 coverage（匹配度）
support_event_types:       # 支持该逻辑的事件类型
invalidating_events:       # ★ 失效条件（不得为空，INV-TT1）
  - {event_type, severity, match_condition, description}
open_question_templates:   # 「待确认」模板（§24）
catalyst_ladder:           # 催化剂强度阶梯（0~100）
default_weights:           # 维度权重覆盖
risk_factors:              # 风险因素与权重
evidence_requirements:     # 最低证据要求
anti_patterns:             # ★ 本策略特有的反例警示（来自 §5.6）
```

---

> **权重硬约束**：每个策略的正向维度权重合计必须恰为 **0.95**（`RISK` 不在正向权重表内，
> 而是以最高 15 分的扣分形式出现）。代码里 `_weights()` 在导入时就会校验，
> 算错立即报错而不是静默漂移。

## 3. 策略 1 · `restructuring` 重组预期 ★ 本轮实现

```yaml
user_goal: 寻找经营困难、但近期出现重大资产重组、控制权变化、资产注入或破产重整迹象的公司
description: 公司处于经营困境，同时出现重组/控制权/资产注入迹象，因此存在潜在重组预期
```

### 核心条件（用于 coverage）

| # | 条件 | 数据来源 | 权重 |
|:---:|---|---|:---:|
| C1 | 出现重大资产重组相关公告（A 类） | `Event(RESTRUCTURING)` | 0.35 |
| C2 | 存在控制权 / 实际控制人变化 | `Event(CONTROL_CHANGE)` + `Company.actual_controller` 变化 | 0.25 |
| C3 | 存在资产注入或资产置换迹象 | `Event(ASSET_INJECTION)` | 0.20 |
| C4 | 经营困境背景（连续亏损 / 净资产承压 / ST） | `FinancialMetric` + `Company.is_st` | 0.20 |

> `coverage = Σ 命中条件权重`。§17 示例的 `94% MATCH` 对应 C1+C2+C3 命中 + C4 部分命中。

### 支持事件类型

```
RESTRUCTURING · ASSET_INJECTION · CONTROL_CHANGE · BANKRUPTCY_REORGANIZATION · M&A
```

### 失效条件（★ 不可为空）

| event_type | severity | match_condition | 描述 |
|---|:---:|---|---|
| `RESTRUCTURING` | terminal | `title_contains: ["终止", "失败", "撤回"]` | 重组终止 / 重大资产重组失败 |
| `CONTROL_CHANGE` | severe | `title_contains: ["取消", "终止", "解除"]` | 控股权变更取消 |
| `REGULATORY_RISK` | terminal | `title_contains: ["否决", "不予核准", "终止审查"]` | 监管否决 |
| `ASSET_INJECTION` | severe | `title_contains: ["退出", "放弃", "不再纳入"]` | 核心资产退出 |
| `LITIGATION` | severe | `amount_ratio > 0.3` | 重大诉讼致交易基础受损 |

### 待确认模板

```
✓ 已确认：重大资产重组公告 / 控股股东发生变化 / ST 状态
? 待确认：交易标的 · 交易价格 · 重组方案 · 资产评估结果 · 监管审核结果 · 股东大会决议
```

### 催化剂强度阶梯

| 阶段 | 识别依据 | 分值 | 早期？ |
|---|---|:---:|:---:|
| 存量｜重组已完成 | 限售股解禁、持续督导、过户完成 | 5 | ✗ |
| 早期｜筹划 / 停牌 / 意向协议 | 筹划重大事项、停牌筹划、意向协议 | 10 | **✓** |
| 早期｜预重整 / 重整申请 | 预重整、债权人申请重整、破产申请 | 15 | **✓** |
| 早期｜法院受理 / 指定管理人 | 法院裁定受理、指定管理人 | 28 | **✓** |
| 早期｜阶段未知 | 有重组/重整类公告但未识别到阶段关键词 | 20 | **✓** |
| 进展｜预案披露 | 重组预案、发行股份购买资产预案 | 40 | ✗ |
| 进展｜草案 + 评估 | 重组报告书草案、资产评估结果 | 60 | ✗ |
| 进展｜获批复 / 审核通过 | 国资批复、审核无条件通过 | 72 | ✗ |
| 进展｜股东大会通过 | 股东大会决议公告 | 80 | ✗ |
| 完成｜监管核准 / 实施完成 | 证监会核准、资产过户完成 | 95 | ✗ |
| 终止 / 失败 | 终止公告 | **0 + 触发失效** | ✗ |

> **「早期」是阶段，不是事件类型。** 刻意**没有**新增 `PRE_RESTRUCTURING`
> 之类的枚举 —— 实测吃过一次苦头：`RESTRUCTURING` 与 `M&A` 语义重叠
> 导致 9/15 误判、`C1` 静默不命中。阶段由确定性关键词识别（规则层，规格 §28），
> 事件类型保持不变。
>
> **低分不等于不重要**：分数表示「离价值兑现的距离」。
> 早期苗头分数低是因为确定性低、兑现远 —— 因此它排在后面，
> 并且**必须在卡片上标注阶段**，否则用户会把苗头当成确定的事（违反规格 §24 / §38）。
>
> **存量阶段（限售股解禁）**：按用户抽样核对判断**保留召回**（它确实是重组事件），
> 但催化强度接近零。原因是这类公告在每单重组完成后会**连续产生数年**，
> 给正常催化分会持续制造幻影机会。

### 权重与风险

```yaml
default_weights:
  THESIS_MATCH: 0.30 · EVENT_CATALYST: 0.25 · CATALYST_STRENGTH: 0.10
  CERTAINTY: 0.10 · FUNDAMENTALS: 0.05 · SHAREHOLDER_STRUCTURE: 0.10
  MARKET_ATTENTION: 0.05 · HISTORY_CASE: 0.00
risk_factors:
  事件失败可能性: 0.30   # 历史终止记录、方案未定、审批未完成
  监管 / 合规风险: 0.25  # 问询未回复、监管函
  公司基本面恶化: 0.20   # 连续亏损、退市风险
  大股东质押 / 资金占用: 0.15
  可交易性: 0.10         # 停牌
evidence_requirements: { A: 1 }   # 至少 1 条 A 类证据
# 早期信号（预重整 / 重整申请 / 法院受理 / 筹划停牌）同样要求 A 类证据：
# 苗头可以低确定性，但不能是无来源的传闻（规格 §16）
```

### ⚠️ 本策略的反例警示（来自 §5.6 示例 A / 示例 J）

| 反例 | 处理 |
|---|---|
| **ST ≠ 重组预期**。规格示例 J 明确指出：困境反转**不应依赖** ST 标签 | `is_st` 只作为 C4 的**部分**证据（权重 0.20 内的一部分），且**禁止**出现「`is_st=true` → 命中重组策略」的直接规则（INV-C1） |
| **有重组公告 ≠ 重组会成功** | 确定性维度必须计入未确认事项与历史失败记录；风险维度必含「事件失败可能性」 |
| 重组预期**不是**只看 ST | 支持事件类型覆盖非 ST 公司的资产注入与产业整合 |

## 4. 策略 2 · `turnaround` 困境反转

```yaml
user_goal: 寻找过去几个季度业绩较差，但最近出现经营改善迹象的公司
description: 公司可能处于经营周期拐点
```

### 核心条件

| # | 条件 | 判据 | 权重 |
|:---:|---|---|:---:|
| C1 | 过去有明确经营恶化 | 营收连续下降 / 净利润亏损 / 毛利率下降（≥2 期） | 0.20 |
| C2 | 最近出现经营改善迹象 | 营收恢复增长 / 毛利率连续 ≥2 季改善 / 经营现金流转正 | 0.30 |
| C3 | 改善有可归因的具体举措 | 剥离亏损业务 / 降债 / 管理层变化 / 成本改善 / 资产处置 | 0.20 |
| C4 | 行业或公司层面需求恢复 | 行业数据 / 订单恢复 | 0.15 |
| C5 | **不依赖 ST 标签** | 明确允许非 ST 公司（示例 J） | 0.15 |

### 失效条件

| event_type | severity | 描述 |
|---|:---:|---|
| `EARNINGS_TURNAROUND` | terminal | 经营现金流再次转负 / 亏损扩大 |
| `EARNINGS_TURNAROUND` | severe | 毛利率重新恶化 |
| `MAJOR_CONTRACT` | severe | 后续订单明显下降 |
| `REGULATORY_RISK` | severe | 财务造假 / 非标审计意见 |

### 待确认模板（直接来自规格示例 B）

```
? 改善是否具有持续性
? 新订单是否能够转化为收入
? 行业景气是否能够持续
? 改善是否依赖一次性因素（资产处置 / 减值转回 / 政府补助）
```

### 催化剂阶梯

| 阶段 | 分值 |
|---|:---:|
| 单季改善 | 40 |
| 连续两季改善 | 70 |
| 业绩预告上调 | 85 |
| 年报确认 | 95 |

### 权重与风险

```yaml
default_weights:
  THESIS_MATCH: 0.30 · EVENT_CATALYST: 0.10 · CATALYST_STRENGTH: 0.05
  CERTAINTY: 0.10 · FUNDAMENTALS: 0.25 · SHAREHOLDER_STRUCTURE: 0.05
  MARKET_ATTENTION: 0.05 · HISTORY_CASE: 0.05
risk_factors:
  改善不可持续: 0.35 · 一次性因素驱动: 0.20 · 行业景气回落: 0.20 · 财务质量: 0.25
```

### ⚠️ 反例警示（示例 B / 示例 J）

| 反例 | 处理 |
|---|---|
| 「业绩大涨，所以看好」 | §5.6 示例 B 明确禁止。必须形成 Thesis 语句并列出 `Supporting Evidence / Uncertainties / Invalidating Events` 三段 |
| 「困境反转必须找 ST」 | 示例 J 明确否定。C5 条件反向计分：**刻意不依赖 ST** |

## 5. 策略 3 · `event_driven` 事件驱动

```yaml
user_goal: 关注单一重大事件对公司的影响
description: 存在明确的单一催化事件，事件结果将显著影响公司基本面或市场预期
```

### 核心条件

| # | 条件 | 权重 |
|:---:|---|:---:|
| C1 | 存在明确的单一事件（A/B 类证据） | 0.35 |
| C2 | 事件金额 / 规模对公司具备显著影响（≥ 营收或净资产的显著比例） | 0.25 |
| C3 | 事件有可预期的后续节点（进展可跟踪） | 0.20 |
| C4 | 事件方向明确（非「可能筹划」等模糊表述） | 0.20 |

### 支持事件类型

```
M&A · BUYBACK · SHAREHOLDER_BUY · SHAREHOLDER_SELL · POLICY_CATALYST
MAJOR_CONTRACT · NEW_PRODUCT · ASSET_INJECTION · MANAGEMENT_CHANGE
DIVIDEND_POLICY · LITIGATION · REGULATORY_RISK
```

### 失效条件

```
事件被取消 / 终止 / 失败 / 撤销    → terminal
事件规模被大幅下调                → severe
事件影响被证明与预期不符          → severe
```

### 催化剂阶梯

```
市场传闻 20 → 正式公告 40 → 进展公告 60 → 实施完成 85 → 效果确认 95
```

### 权重与风险

```yaml
default_weights:
  THESIS_MATCH: 0.30 · EVENT_CATALYST: 0.25 · CATALYST_STRENGTH: 0.15
  CERTAINTY: 0.10 · FUNDAMENTALS: 0.05 · SHAREHOLDER_STRUCTURE: 0.05
  MARKET_ATTENTION: 0.05 · HISTORY_CASE: 0.00
risk_factors:
  事件失败: 0.35 · 影响被高估: 0.25 · 短期炒作后回落: 0.20 · 基本面: 0.20
```

### ⚠️ 反例警示

| 反例 | 处理 |
|---|---|
| 「事件驱动 = 不看基本面」 | `FUNDAMENTALS` 权重降为 0.05 但**不为 0**；风险维度必含基本面因素 |
| 「有事件就加分」 | C4 要求事件方向明确；模糊表述（「拟筹划」「正在论证」）不得计入 C1 |

## 6. 策略 4 · `ma_integration` 并购 / 产业整合（规格示例 F）

```yaml
user_goal: 寻找行业集中度提升、产业整合，或上市公司通过并购获得新业务的机会
description: 行业集中度提升 + 标的与上市公司业务协同，但必须同时评估交易质量与风险
```

### 核心条件

| # | 条件 | 权重 |
|:---:|---|:---:|
| C1 | 发生并购 / 收购事件（A 类公告） | 0.25 |
| C2 | 标的与上市公司存在业务协同（同行业 / 上下游 / 产业链） | 0.20 |
| C3 | **交易质量可评估**：收购价格、标的盈利能力、资产质量可获取 | 0.25 |
| C4 | 行业集中度正在提升（行业层面证据） | 0.15 |
| C5 | 新增业务确实进入上市公司体系（非仅意向） | 0.15 |

### 必须调查清单（§5.6 示例 F 明确要求）

```
收购价格 · 商誉风险 · 业绩承诺 · 并购标的盈利能力
资产质量 · 融资方式 · 整合难度 · 历史并购表现
```

> **这 8 项不是可选项。** 系统必须逐项给出「已获取 / 未获取」，未获取的进入 `OpenQuestion`。

### 失效条件

```
并购终止 / 失败                        → terminal
业绩承诺未达标                          → severe
商誉大额减值                            → terminal
整合失败（管理层变动 / 业务剥离）        → severe
```

### 催化剂阶梯

```
意向协议 30 → 正式方案 55 → 过会 / 交割 80 → 整合见效（需 ≥1 年） 95
```

### 权重与风险

```yaml
default_weights:
  THESIS_MATCH: 0.30 · EVENT_CATALYST: 0.20 · CATALYST_STRENGTH: 0.05
  CERTAINTY: 0.10 · FUNDAMENTALS: 0.10 · SHAREHOLDER_STRUCTURE: 0.05
  MARKET_ATTENTION: 0.05 · HISTORY_CASE: 0.10   ← 权重交给历史并购表现
risk_factors:
  商誉减值: 0.25 · 整合失败: 0.25 · 高溢价收购: 0.20
  标的盈利不达预期: 0.20 · 融资摊薄: 0.10
```

### ⚠️ 反例警示（§5.6 示例 F）

> **「发生并购」≠「一定是好机会」。系统必须同时分析：催化剂 + 交易质量 + 风险。**

`HISTORY_CASE` 权重提升到 0.10，正是因为「历史并购表现」是判断交易质量的关键输入。

## 7. 策略 5 · `shareholder_action` 股东行为（规格示例 G）

```yaml
user_goal: 关注公司管理层或主要股东用真金白银表达信心的情况
description: 控股股东 / 管理层 / 公司自身通过增持或回购表达信心
```

### 核心条件

| # | 条件 | 权重 |
|:---:|---|:---:|
| C1 | 控股股东 / 管理层增持，或公司回购 | 0.30 |
| C2 | 规模显著（相对市值 / 流通股比例） | 0.20 |
| C3 | **资金来源可评估**（§5.6 示例 G 明确要求） | 0.20 |
| C4 | 公司现金流稳定、负债可控 | 0.20 |
| C5 | 无大股东质押风险 | 0.10 |

### 必须检查清单（§5.6 示例 G）

```
增持资金来源 · 增持规模 · 增持价格区间 · 历史增持后的表现
公司现金流 · 是否存在高负债 · 是否存在大股东质押
```

### 失效条件

```
增持计划未实施 / 提前终止        → severe
回购未执行 / 大幅缩水            → severe
出现减持                          → terminal
资金来源暴露问题（占款 / 违规）  → terminal
```

### 催化剂阶梯

```
计划公告 40 → 开始实施 60 → 实施完成 70 → 后续无减持（观察期内） 95
```

### 权重与风险

```yaml
default_weights:
  THESIS_MATCH: 0.30 · EVENT_CATALYST: 0.15 · CATALYST_STRENGTH: 0.05
  CERTAINTY: 0.10 · FUNDAMENTALS: 0.10 · SHAREHOLDER_STRUCTURE: 0.20
  MARKET_ATTENTION: 0.05 · HISTORY_CASE: 0.00
risk_factors:
  增持 / 回购计划未实施或缩水: 0.20   # ★ §14.3：必须有「事件可能失败」类风险
  增持规模过小（象征性）: 0.20 · 资金来源存疑: 0.20
  大股东质押: 0.15 · 历史增持后表现差: 0.15 · 高负债: 0.10
```

### ⚠️ 反例警示（§5.6 示例 G）

> **AI 不应只做正向判断。** `hunt_risk` 节点对本策略为**强制**：必须输出上述 7 项检查中
> 至少 3 项的反向结论（若确实无问题，须显式说明「已检查 X/Y/Z，未发现问题」）。

## 8. 策略 6 · `policy` 政策驱动（规格示例 E）· 自上而下入口

## 14. 三条跨策略硬约束（写死在代码里，不靠 prompt）

### 14.1 策略决定「为什么被发现」，标签不决定策略（§5.6 示例 J）

> **投资策略应该决定股票为什么被发现，而不是股票标签决定投资策略。**

```
❌ 禁止：is_st == True            → 命中 restructuring
❌ 禁止：industry == "新能源"     → 命中 policy
❌ 禁止：announcement_type == "并购" → 命中 ma_integration
✅ 正确：先由策略定义「什么条件组合构成该 Thesis」，再从数据中寻找
```

**实现要求**：`strategies/*/rules.py` 只允许读取**策略自身定义的条件**，
不得提供 `match_by_tag()` 这类按标签直接映射的接口。INV-C1 由代码审查 + 单测保障。

### 14.2 顺序门控（用于 policy / product 两条链路型策略）

| 策略 | 门控规则 |
|---|---|
| `policy` | C5（实际订单/收入验证）未命中 → `coverage` 上限 **0.45** |
| `product` | C3（客户验证）未命中 → C4、C5 一律计 **0** |

### 14.3 「发生 X」≠「X 会成功」

所有策略的风险维度**必须**包含「事件失败可能性」类因素。
不存在「某个事件类型命中即加分且无对应风险项」的策略配置。

## 15. 同一公司可对应多个 Thesis（§5.7）

规格示例 K：一家公司同时有 `控股权变化 + 资产注入 + 行业周期反转 + 业绩改善`。

```
公司 K
  ├─ restructuring        对用户 A（重组预期 40%）→ match 95%
  ├─ turnaround           对用户 B（困境反转 40%）→ match 82%
  ├─ cycle                对用户 C（行业周期 40%）→ match 76%
  └─ growth               对用户 D（成长投资 40%）→ match 48%
```

**实现约束**：`opportunity` 表唯一键为 `(company_id, profile_id, thesis_id)`，
天然支持同一公司在同一画像下产生**多条** Opportunity（不同 Thesis），
也支持同一 Thesis 在不同画像下产生**多条** Opportunity。

> 这是「雷达不是自选股列表」在数据模型上的体现。
