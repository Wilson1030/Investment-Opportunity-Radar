## D01 · 产品定位

**决定**：本系统是「投资机会发现与研究辅助系统」。核心输出不是股价，而是**「为什么这只股票现在值得你关注」**。

**产品要回答的 7 个问题**
1. 发生了什么？ 2. 为什么这个事件可能重要？ 3. 为什么它与你的投资倾向有关？
4. 有哪些证据支持？ 5. 当前机会处于什么阶段？ 6. 哪些信息仍需确认？
7. 后续什么事件会强化或破坏当前逻辑？

**明确不是**：股票行情软件 / K 线分析工具 / 技术指标工具 / 自选股列表 / 纯选股器 / 纯 AI 荐股器 / 纯新闻聚合器。

**信息层级（用户看到的顺序）**
```
① 发生了什么 ② 为什么重要 ③ 为什么与我有关 ④ 有什么证据
⑤ 哪些地方还不确定 ⑥ 风险是什么 ⑦ 下一步看什么
```
而非 `价格 → 涨跌幅 → K线 → MACD → RSI → PE`。

**代价**：不能复用成熟行情软件的信息架构，所有页面需从「事件叙事」重新设计。
**可逆性**：不可逆 —— 这是产品身份，不是实现选择。

## D02 · 使用形态

**决定**：本地单用户。代码与表结构中**预留 `user_id` / `profile_id` 外键**，但**不实现账号、鉴权、多租户隔离**。

**理由**：Owner 自用研究工具；多用户会引入鉴权、租户隔离、任务队列、部署运维，复杂度和工期是数倍，而 MVP 的价值验证完全不需要它们。

**代价**：无法多人共享；无鉴权（仅监听 localhost）。
**可逆性**：低 —— 表结构已预留，加账号体系不用改表；但并发抓取与数据隔离逻辑需要新写。
**复议条件**：仅当确认需要多人协作研究时复议。

## D03 · 交付边界

**决定**：第一轮交付「骨架 + 文档 + 计划」：架构可评审、可启动、可插入业务逻辑。
不交付：跑通真实 LLM 全流程、向量检索、多空辩论、前端接真实 API。

**理由**：产品规格 3094 行，直接编码会在后期暴露设计缺陷并返工。文档先行的评审成本最低。

## D04 · 技术栈

**决定**
```
后端  Python 3.13 · FastAPI · SQLModel · Alembic · Pydantic v2 · SQLite
前端  Node 22 · Vite · React 18 · TypeScript · Tailwind CSS
采集  akshare · httpx · BeautifulSoup4 · pdfplumber（公告 PDF）
AI    httpx 直连各 provider（不引入 LangChain/LangGraph）
调度  APScheduler
```

**理由**
- Python 是 A 股数据生态的唯一现实选择（akshare / PDF 解析 / 财务处理）。
- 规格里的机会卡、评分拆解、证据抽屉、事件时间线、状态流都是**组件化交互**，需要真正的前端组件能力，Jinja2+HTMX 会写得别扭。
- SQLModel 让 Pydantic schema 与 ORM 表定义合二为一，减少一层重复。
- **不引入 LangChain/LangGraph**（见 D06），AI 层只需要「结构化输出 + 缓存 + 重试」，框架带来的状态抽象在这里是负债。

**代价**：两个进程、一套前端构建；SQLite 并发写能力有限（单用户可接受）。
**可逆性**：中 —— `DATABASE_URL` 改为 Postgres 即可上量；前端可独立替换。

## D05 · 前端视觉基调

**决定**：深色研究终端风。

```
底色 #0B0E11   面板 #12161C   边框 #1F262E
主文 #E6E9EF   次文 #8B94A3   强调 #2DD4BF
状态色：待确认 #F59E0B · 重点跟踪 #2DD4BF · 逻辑成立 #22C55E · 逻辑失效 #EF4444
数字一律等宽字体（tabular-nums）；信息密度高；用分隔线而非卡片阴影组织。
```

**理由**：与「雷达扫描」隐喻契合；高信息密度符合研究场景；避免「荐股 App」的视觉语言。

**代价**：长文本可读性弱于浅色；需要谨慎控制对比度与行高（正文行高 ≥ 1.7）。
**可逆性**：中 —— 通过 Tailwind 主题变量集中管理，换肤成本可控。

## D06 · AI 架构 ★ 关键决策

**决定**：**自研轻量节点管道**，每个节点是 **JSON → JSON 纯函数**。不引入 LangGraph。

```
doc → extract_event() → classify_thesis() → hunt_risk() → analyze() → card
```

**理由（核心是可逆性）**

| 维度 | 轻量管道（选定） | LangGraph |
|---|---|---|
| 控制流 | 显式函数调用，固定 DAG | 状态机图，运行时驱动，支持循环/条件边 |
| 状态 | 函数参数传递，显式局部 | 共享 State + reducer 合并，全局但难追 |
| 缓存/重跑 | 纯函数，按 `(输入哈希, prompt_version)` 缓存天然成立 | 缓存需手工包裹节点；重跑=重放图+checkpointer |
| 成本 | 函数级缓存直接决定 API 账单 | 缓存粒度模糊 |
| 多空辩论 | 需自写轮次/终止/上下文管理 | 主场能力 |
| 依赖 | 零框架依赖，pdb 可用 | 多一层框架，0.x→1.x 曾破坏性变更 |

**决定性论据**：管道 → LangGraph 只需写一个 `graph.py` 把现有纯函数包成节点，**一天可迁移**；LangGraph → 管道则状态形状已被框架绑定，**需重写**。故「先管道」是可逆决策。

**代价**：多空对抗、人工中断、断点续跑需自己实现（MVP 不需要）。
**可逆性**：**高（刻意设计）**。约束：所有节点**必须**保持纯函数签名 `f(input: dict) -> dict`，禁止在节点内直接读写数据库或全局状态。
**复议条件**：需要多空辩论 / 人工中断审核 / 复杂条件回退时。

## D07 · LLM 分层与模型

**决定**：provider 抽象层预留全部候选（Ollama / DeepSeek / OpenAI / Kimi / GLM / Claude），**开发与测试期默认本机 Ollama `qwen3:4b`**，云端 key 不作为运行前提。

```
抽取层 EXTRACT_*  量大、任务简单、要求 JSON 稳定 → qwen3:4b（本地）
分析层 ANALYZE_*  量小、需要推理 → qwen3:4b（本地，可切 deepseek-reasoner）
```

**理由**
- 全部模型预留 = 不被单一供应商锁定，切换只改 `.env`。
- 开发期全本地 = 零 API 成本，可反复试错不心疼；公告全文不出本机。
- 抽取层可换云端 = 一旦本地 JSON 合规率不达标，改两行配置即可。

**代价**：4B 模型的中文公告抽取质量与 JSON 合规率**未实测**，可能需要在 prompt 与重试策略上多花功夫；本地推理速度慢。
**可逆性**：高 —— 节点内部只调用 `LLMProvider.complete()`，换 provider 不改业务代码。
**必须记录**：每条 LLM 结果存 `model` + `prompt_version`，以便换模型后计算出哪些结论需要重跑。

## D08 · 评分：双分制

**决定**：并行维护两个分数，**规则分为主分**（参与排序、可点击拆解），**LLM 分为辅分**（仅详情页出现，用于分歧提示）。

```
rule_score      确定性规则加权，每项加减分绑定证据 → 可复现、可审计、可调参
semantic_score  LLM 语义判断，只回答「规则没覆盖到的因素」→ 不可复现，不参与排序
divergence      |rule - semantic| > 20 → 标红「规则与语义分歧，建议人工复核」
```

**理由**：规则分满足规格 §12/§13 的「可解释、可追溯、可调参」；LLM 分补足规则盖不到的语义因素（交易对手方质地、公告措辞变化）。**两者分歧本身是有价值的研究信号。**

**代价**：两个数字可能让用户困惑 → UI 上必须明确主次。
**可逆性**：中。

## D09 · 数据源

**决定**：akshare（行情/财务/新闻）+ 巨潮资讯 cninfo（公告列表与全文）直连；采集层抽象为 `DataSourceAdapter`，付费源（Tushare/Wind/Choice）作为未来 Adapter 接入，**不改上层**。

**理由**：全免费、无 token 门槛；已在同类项目验证可行。
**代价**：接口稳定性与字段规整度不如付费源；**cninfo 反爬与 PDF 质量是本项目最大工程风险**。
**可逆性**：高。
**必须做**：解析失败率、字段缺失率作为**可观测指标**输出，而不是假装解析总能成功。

## D10 · 证据链深度

**决定**：下载公告全文 → 解析正文 → 按段落切分入库。`Evidence.relevant_text` 指向**具体段落**，带 `page` / `para` 可定位。

```
evidence {
  source_url, publication_time, document_id,
  relevant_text: "……公司控股股东拟以协议转让方式向 XX 集团转让……",
  page: 2, para: 7, reliability_level: A, extracted_facts: [...]
}
```

**扫描件降级路径**：存链接 + 标记 `needs_ocr`，不阻塞流程（`ENABLE_OCR=false` 为本轮默认）。

**理由**：规格 §15 要求「每一个 AI 判断尽可能绑定 Evidence ID + 原文段落」。若只存链接，证据链退化为「公告级」，用户无法核对，幻觉无法发现。
**代价**：要处理 PDF 双栏、表格、扫描件、编码问题。
**可逆性**：中。

## D11 · 采集范围

**决定**：本轮 `INGEST_SCOPE=st_and_risk_warning`。

```
ST / *ST 全量名单           ~180 只
近 90 天有重组类公告        ~150 只
近 90 天控制权/实控人变更    ~80 只
去重后                      ~300 只
→ 每日新增公告 30~80 条 → 本机 4B 可当晚跑完
```

**理由**：与「重组预期先做」的策略顺序一致；量级适配本机慢模型，能真正跑完一轮并验证链路。
**代价（必须承认）**：会漏掉规格示例 F（并购整合）、示例 J（非 ST 的困境反转）、高股息/成长类机会。
**可逆性**：**高 —— 改一行配置 `INGEST_SCOPE=all_a_shares`。** 但需云端模型或多进程支撑（全市场日增 1000~2000 条公告）。

## D12 · 调度

**决定**：APScheduler + 交易日历，三段式：

```
08:30            全量   公告 / 新闻 / 财务 → 事件识别
每 30 分钟       增量   仅拉取 cninfo 最新公告（去重后处理）
15:30            重算   评分 + Thesis 监控 + 失效检测
```

**先 dry-run**：`INGEST_DRY_RUN=true` 时只打印不写库，连续观察 3 个交易日确认数据质量后再开真写。

**理由**：兼顾「今日机会」（盘前）与「持续跟踪 / 逻辑失效提醒」（盘后）。增量抓取对 cninfo 友好。
**代价**：交易日历本身依赖数据源（计划用 akshare 交易日接口）；取不到时退化为「工作日 = 交易日」，节假日会空跑。
**可逆性**：高 —— `SCHEDULER_ENABLED=false` 即回到纯手动。

## D13 · 策略范围与顺序

**决定**：**设计全量，实现逐个**。

```
docs/06-策略设计总表.md  →  10 类 Thesis 的统一字段设计（全部完成）
app/strategies/registry.py  →  10 个策略全部注册
   restructuring      = implemented   ← 本轮唯一
   其余 9 个           = designed（schema 已定，实现待排期）
```

**理由**：规格 §55 明确建议第一阶段先完整实现「重组预期」。若边做边设计，第 4 个策略做到一半会发现与第 1 个的 Event 枚举 / 评分字段 / 状态机不兼容，重构成本高于一次设计到位。
**代价**：本轮用户只能看到重组预期一类机会。
**可逆性**：高。

**实现顺序（建议）**
```
1. restructuring    重组预期      ← 先做（事件文本特征最明显、生命周期最清晰）
2. turnaround       困境反转      （不依赖 ST，验证策略与标签解耦）
3. event_driven     事件驱动      （增持/回购/重大合同，验证行情无关性）
4. ma_integration   并购整合      （验证「催化剂 + 交易质量 + 风险」三维）
5. shareholder_action 股东行为
6. policy           政策驱动      （验证 Macro→Industry→Company 下行链路）
7. cycle            行业周期      （验证 Industry 级机会入口）
8. growth           成长
9. product          技术/新产品
10. value           价值/高股息
```

## D14 · 与 Aura-Hybrid Stock System 的边界

**决定**：**完全零耦合。**

- 不 import 任何 Aura 代码
- 不调用 Aura 的 `localhost:9000`
- 不共用 `.env`、不共用 conda 环境
- 独立 git 仓库、独立数据目录、独立文档

**理由**：用户明确要求两个项目分开；且 Aura 仍在 v0.1.0 开发中，耦合会让 Radar 的可用性被另一个不稳定项目绑定（接口变动 → Radar 静默失效）。
**代价**：采集层部分重写（行情/财务的取数逻辑与 Aura 有重叠劳动）。
**可逆性**：中。**不复议。**

## 附：需求澄清会话中被否决的方案

| 被否决 | 原因 |
|---|---|
| 只出文档不写代码 | 用户选择「骨架 + 文档 + 计划」，要一个可启动的骨架 |
| 服务器多用户 SaaS | 用户明确：后期也不用 SaaS |
| 脚本/Notebook + 静态报告 | 规格 §17/§18/§20/§36 要求的交互与状态流无法体现 |
| Python 全栈 Jinja2 + HTMX | 评分拆解、证据抽屉、时间线等重交互会很别扭 |
| Next.js 全栈 | A 股数据采集与 PDF 解析生态弱；与 Python 资产割裂 |
| LangGraph（本轮） | 见 D06 可逆性论证 |
| 单次大 Prompt 直出 | 上下文超限、无法绑定证据 ID、不可缓存、幻觉难定位 |
| 五策略齐上但都浅 | 无 Thesis / 无待确认 / 无失效条件 → 退化为「带 AI 摘要的选股器」 |
| LLM 直接打分作为主分 | 不可复现、不可审计、无法调参、与用户画像权重脱节 |
| 全部用同一个云端模型 | 抽取环节按强模型单价付费，量大后账单明显 |
| 全 A 股扫描（本轮） | 日增 1000~2000 条公告，本机 4B 模型跑不完一轮 |
| 只存公告元数据 + 链接 | 证据链退化为「公告级」，用户无法核对原文 |
| 复用 Aura 作为数据服务 | 与「两项目分开」诉求冲突，且绑定不稳定依赖 |
| 复用现有 `stock` conda 环境 | 依赖版本已被其他项目钉住，冲突排查成本高 |
