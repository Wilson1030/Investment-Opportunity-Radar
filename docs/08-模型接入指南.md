# 08 · 模型接入指南

> **默认零配置**：不装任何 API key，用本机 Ollama 就能跑通全流程。
> 想换云端模型？**只改 provider 名字 + 填 key**，端点已内置，不用记 base_url。

---

## 1. 默认：本机 Ollama（零成本、内容不出本机）

```bash
# 1) 装 Ollama（https://ollama.com/download）
# 2) 拉模型
ollama pull qwen3:4b
# 3) 确认在跑
curl http://127.0.0.1:11434/api/tags
```

`.env` 保持默认即可：

```bash
LLM_MODE=dev
EXTRACT_PROVIDER=ollama
EXTRACT_MODEL=qwen3:4b
ANALYZE_PROVIDER=ollama
ANALYZE_MODEL=qwen3:4b
```

**实测性能**（RTX 级显卡，qwen3:4b，已关闭思考模式）：

| 环节 | 单条耗时 |
|---|---|
| 公告抽取（`extract_event`） | 约 7 秒 |
| 分析节点（`hunt_risk` / `analyze` / `score_semantic`） | 约 3~5 秒 |

→ 6 个机会（12 条公告 + 18 次分析）约 **1 分钟**；
→ 80 条公告/日约 **10 分钟**。日常完全够用。

| `openai` | OpenAI 兼容 | `https://api.openai.com/v1` | `OPENAI_API_KEY` |

## 3. 三种运行模式

```bash
# dev（默认）：未显式配置 provider 时走本机 Ollama
#   —— 但**若你显式写了** EXTRACT_PROVIDER=deepseek，会尊重你的配置
LLM_MODE=dev

# cloud：各层都走自己的配置
LLM_MODE=cloud

# hybrid：抽取层本地（省钱、公告不出本机）+ 分析层云端（质量高）
LLM_MODE=hybrid
```

**推荐 `hybrid`**：抽取是量大且简单的结构化任务，本地 4B 完全胜任；
分析（找反证、写叙事）需要更强的推理，交给云端更划算。


```bash

```

## 6. 三个已知的坑（都已在代码里处理，但值得知道）

### 6.1 思考型模型（qwen3 等）的推理 token 会吃掉输出上限

qwen3 是思考型模型，**推理 token 也计入 `num_predict`**。不关思考时，
2500 token 会被推理吃光、正文一个 token 都轮不到 ——
表现为「抽取未通过 Schema 校验」，极易误判成模型能力问题。

```bash
LLM_DISABLE_THINKING=true   # 默认已开
```

关掉后的实测效果：单条抽取 **73 秒 → 6.9 秒（11 倍）**。
抽取是结构化转换，不需要推理。

### 6.2 输出必须有上限，否则模型陷入重复生成会跑飞

```bash
LLM_MAX_OUTPUT_TOKENS=2500   # 默认
```

不设上限时，模型一旦进入重复生成循环就会一直输出到上下文上限 ——
实测有一次单条跑了 **21 分钟**仍未结束。但**上限也不能设太小**：
设成 900 时正常输出的 JSON 被截断，实测 5/5 抽取全部 schema 失败。

### 6.3 只给 `format: "json"` 不约束字段，小模型会「复读输入」

曾经踩过的坑：`analyze` 与 `score_semantic` 节点 **6/6 校验失败**，
`raw_output` 里是**输入数据本身** —— 小模型在「要求 JSON + 输入是一大段 JSON」时
会直接把输入抄回来。

现在改为**结构化输出**：把输出模型的 JSON Schema 传给 Ollama 的 `format`
（服务端做语法约束，模型无法输出不符合结构的对象）。Ollama 0.5+ 支持。

> 若你用的 provider 不支持结构化输出，代码会自动退化为普通 `json` 模式，
> 由 `NodeRunner` 的「校验失败 → 把错误回灌给模型重试」兜底。

## 7. 本地模型的已知能力边界（诚实说明）

用 `qwen3:4b` 跑分析层时观察到的行为：

| 项 | 表现 | 说明 |
|---|---|---|
| 抽取（`extract_event`） | ✅ 12/12 通过，分类准确 | 结构化转换是它的强项 |
| 反证检索（`hunt_risk`） | ✅ 6/6 通过，能列出风险 | 但 `evidence_ids` 常为空 —— 它不主动引用证据 ID |
| 研究叙事（`analyze`） | ✅ 6/6 通过，叙事可用 | 文案偏模板化 |
| 语义分（`score_semantic`） | ⚠️ 6/6 通过，但**总是返回规则分** | 于是 `divergence` 恒为 0，分歧提示从不触发 |

**关于语义分**：这符合 prompt 的约束（「若你认为规则已覆盖全部因素，直接返回
`rule_score`」），4B 模型倾向保守地回答"规则都覆盖了"。
要想让语义分真正提供增量视角，把**分析层换成更强的云端模型**即可：

```bash
LLM_MODE=hybrid
ANALYZE_PROVIDER=deepseek
ANALYZE_MODEL=deepseek-reasoner
DEEPSEEK_API_KEY=sk-xxxxxxxx
```

代码无需任何改动 —— 这正是把 provider 抽象出来的意义。

## 8. 排错

| 现象 | 检查 |
|---|---|
| `Ollama 调用失败` | `ollama serve` 是否在跑？`/api/health` 的 `llm.reachable` |
| `schema_failure_rate` 偏高 | 看 `/api/admin/llm-runs?status=schema_error` 的 `error`；区分「被输出上限截断」与「模型输出错」 |
| 单条耗时异常长 | 是否有别的进程在抢 GPU（**我踩过：自己的诊断命令让 pipeline 慢了 3 倍**） |
| 换了 provider 不生效 | 确认 `LLM_MODE`；`dev` 模式下**显式配置的 provider 是会被尊重的**（历史 bug 已修） |
| 配置写了但不生效 | 跑 `pytest tests/test_ai_nodes.py -k env_example` —— 会校验 `.env.example` 里的变量是否真实存在 |
